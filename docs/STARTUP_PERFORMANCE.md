# Windows 启动性能

## 2026-09-21 本机测量

桌面快捷方式指向 Windows PowerShell 的 `start.ps1`。用户报告浏览器已打开、命令行立即出现，但网页约十秒后才打开。此现象的完整十秒延迟尚未复现，不能据此归因于数据库或浏览器。

已确认的问题：桌面持久化 PATH 中没有 Node，原 `Get-Command node` 会触发 PowerShell 模块搜索后才回退到本机已有运行时；单独查找测得 1166 ms。Codex 进程的 PATH 已包含运行时，会掩盖这段开销。即使加 `-CommandType Application`，缺失命令的实测冷启动仍有这段延迟，因此改成直接逐项检查 PATH 中的 `node.exe`。

对比在同一机器、桌面持久化 PATH、Windows PowerShell 5.1、Node 24.19.0 下进行。每轮复制启动脚本到随机 `.tmp` 目录，使用本项目真实服务器模块、独立空数据/Vault、动态分配的回环端口。只终止本轮临时服务；未重启、读取或复制用户的真实数据。使用 `-NoBrowser`，计时从启动 PowerShell 子进程到其退出，包含解释器加载。

| 场景 | 原版三轮（ms） | 优化后三轮（ms） |
| --- | --- | --- |
| 服务冷启动，空的合成资料库 | 1914 / 1819 / 1848 | 726 / 681 / 688 |
| 服务已运行，再次打开 | 1461 / 1461 / 1454 | 270 / 262 / 280 |

这里的冷启动指服务未运行，操作系统文件缓存可能已预热，不代表重启电脑后的首次磁盘读取。单独调用默认浏览器的分派测得 48 ms，**不包含页面完成显示**，不可直接与表格相加作为端到端验收。

## 修改内容

- 先在启动器进程内检查回环服务。已运行时直接打开浏览器，不查找 Node、不启动版本/探测子进程、不写目录或 PID。
- 未运行时直接检查 PATH，然后使用原有运行时回退路径，保留 Node 24 版本与依赖检查。
- 进程内 HTTP 探测验证首页已知模块入口（`/app.mjs` 或 `/review-entry.mjs` 的完整 script 标签），禁用代理发现与重定向；TCP 预检限制未监听端口的等待，防止 .NET Framework 的连接重试把冷启动拉长。
- 就绪轮询从固定先等 250 ms 改为立即检查、间隔 50 ms；保留子进程退出检测和有界等待。
- 提供 `-Timing` 分段输出和 `-Port`，默认端口仍为 4318。后台启动继续隐藏窗口，原有日志和停止入口保留。

## 验证和边界

`node --test tests/launcher.test.mjs` 在 Windows 验证：无需 Node/磁盘写入的服务复用、中文与空格路径、真实服务器在临时数据目录启动、重复启动不替换 PID、拒绝无关页面和重定向、子进程退出时报告失败。Linux 跳过 Windows 启动器测试，其余项目测试照常运行。

应用优化后，用户通过原桌面快捷方式再次测试，反馈“已经接近秒开（约 1 秒以内）”。这是用户在实际使用环境的观察，未使用自动化时钟记录，也不代表重启电脑或浏览器关闭后的冷启动保证。最初近十秒中的每一段仍未完整测量归因。

真实 Vault 大小、Windows 首次加载、杀毒扫描、OneDrive 文件驻留状态、浏览器处理都可能影响耗时，这些目前只是待排查因素，没有实测证据归因。不设置开机常驻、不调整杀毒/同步/浏览器全局设置、不削弱服务权限边界。

若仍有延迟，使用 `start.ps1 -Timing` 区分服务就绪与浏览器分派；注意 `-NoBrowser` 不是只读诊断模式，服务未运行时仍会启动服务。真实资料环境验收不能由空库测试替代。

## 2026-10-17 审阅入口兼容修复

组合候选 `03190b251774e42dc1e22852c5bb272b27c24642` 的 [CI](https://github.com/wmy5555/zhixu-learning-workbench/actions/runs/38998035114) 中，Linux Quality、Secrets、Dependencies 成功；Windows 1177 项中 1176 通过，唯一失败为真实应用启动测试在约 15.6 秒后报告启动超时。原日志未包含服务 stderr 正文，不能据此把并发负载、内存或网络当作已确认原因。

确定的入口冲突是：首页已改为加载 `/review-entry.mjs`，而启动器仅接受包含 `app.mjs` 的响应。即使服务器返回正常首页，该条件仍恒为 false；测试后续的旧入口正文断言也会不匹配。启动脚本及原测试与 main 和四个来源 PR 相同，四源尚未包含统一审阅首页，来源 CI 因而不能发现该组合问题。测试夹具关闭 scheduler，价目网络刷新不在该启动路径中；无须用初始化变慢解释入口误判。

修复只识别两种已知、精确的模块 script 标签，拒绝裸文件名、伪路径、后缀及外站地址。保留 HTTP 200、禁止代理/重定向、15 秒启动界限、50 ms 轮询、退出检查与原 PID 复用；未放宽等待或把任意 HTTP 响应当作本应用。真实启动测试改为比对完整、实际首页，保留冷启动、暖启动及 PID 不变断言。302、201 测试使用合法入口正文，确保状态码和重定向保护本身受测。

跨平台入口回归在旧启动器上先失败；修复后与审阅入口回归合计 20 项通过，7 项 Windows 专用测试在 Linux 明确跳过。Windows 实际启动回归和新精确 SHA 的完整 CI 仍须核验（完整 Windows CI 会执行全部启动回归），不能用这些静态/非 Windows 结果代替。若真实启动再次失败，测试在清理前只输出隔离夹具的 PID/存活状态、HTTP 状态与入口布尔值及有界、脱敏的服务 stderr，不读取凭据文件。
