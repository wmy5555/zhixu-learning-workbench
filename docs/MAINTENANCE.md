# 维护与发布

## 最小维护系统

使用 main + 短期分支 + PR。主分支变更运行 CI；PR 运行同样检查；每周定时运行以发现新增依赖风险；Dependabot 每周提出 npm/pnpm 和 GitHub Actions 更新，不自动合并。

`pnpm-workspace.yaml` 禁止 pnpm 在运行脚本前隐式重装依赖。安装始终显式执行 `pnpm install --frozen-lockfile`；CI 使用干净环境重新安装，而本机验证不会擅自替换正在使用的依赖目录。

必需检查名称：`Quality (ubuntu-latest)`、`Quality (windows-latest)`、`Secrets`、`Dependencies`。Quality 使用 Node 24、固定 pnpm、锁定依赖，运行仓库检查、全部 Node 测试和小型中文检索质量检查。Linux 临时加密密钥仅用于合成测试。Web/Node 部分没有构建/类型系统，因此不设置虚假的 Web 构建/类型检查；Android 构建另按下述检查执行。

Android 共用界面样机另有 `Android build and lint` 检查，使用 JDK 21、Android SDK 36 和固定 Gradle Wrapper，构建应用及本项目设备测试 APK 并执行 lint。涉及样机的 PR 还需此项通过；设备测试 APK 构建成功不等于已在模拟器执行。首次功能交付的视觉和真实点击结果须单独记录，参见 [Android 共用界面](ANDROID_SHARED_UI.md)。

Android 网页基线按所有者要求固定在 `apps/android/web/`，清单见 `apps/android/web-baseline.json`。不要从最新 main/public 自动更新这个快照。网页版大版本后先提交同步范围供所有者确认；只有批准后才改基线。原生功能和手机适配可独立继续。手动 Android workflow 的 `upgrade_baseline` 仅在需要覆盖安装验收时开启，固定第一阶段源码与新 APK 共享本次临时 debug 签名，不上传密钥，不移动旧标签，不作为正式发布签名。

CI 文件不等于服务器端合并保护。Branch protection 是否可用取决于 GitHub 套餐和仓库可见性；不为启用功能擅自变更可见性或付费升级。若服务器不支持，维护 Agent 仍须等待四项检查全部通过，且明确说明不是强制阻断。

2026-09-20 实际配置 main 保护时，GitHub 返回 403，当时私有仓库的套餐不支持此功能。2026-10-02 已核对仓库为 Public，所有者确认公开是其本人决定。旧的套餐限制仅是历史记录；公开状态本身不能证明已启用保护，当前规则须另行读取验证，不能将四项 CI 通过误报为服务器强制保护已完成。

## Windows 文本与路径编码

跨进程文本协议（包括其中的路径）须在发送端和接收端显式使用 UTF-8，不依赖 Windows 默认编码。涉及路径处理的改动，执行一次包含中文和空格路径的定向回归，覆盖本次修改的实际进程边界；按影响范围验证，不因此重复检查无关功能。修复编码处理，不以重命名用户目录规避问题。

## 跨任务交接

统一 PR / 批量合并不得仅因整合再次运行已完成的测试：核对代码、相关依赖和执行条件后复用仍有效证据，仅为新增代码、实际冲突解决或失效证据补直接相关的必要验证。不因统一合并重跑全量或组合测试；保留不可跳过的仓库门禁及强制 CI，遇到冲突须报告，不擅改 CI 配置。

交接只写接收任务需要的目标、已核实证据及其未覆盖范围、依赖或阻塞、下一步动作。产品目标与需求取舍按已确认的用户原始讨论及后续修订核对；来源不可读时，在 [PR 审阅跟进](PR_REVIEW_FOLLOWUP.md) 留待补入口并标明缺口，不公开私聊链接。接收方开始或恢复工作时，重新阅读当前 `AGENTS.md` 和相关维护规则，并核对任务归属、最新状态与当前分支；旧状态摘要不能代替现行规则或最新证据。

证据需绑定精确提交、执行范围、复用依据和未验收项；对现象与成因分别区分已观察、已证实和假设。实质变化只使受影响的证据失效。对输入、异步或导航行为的改动，按影响范围检查草稿保留、重复操作、失败重试、成功后的新意图、导航关闭及库上下文切换；产品路径细节沿用 [README](../README.md)、[引导说明](ONBOARDING.md) 和 [PR 审阅跟进](PR_REVIEW_FOLLOWUP.md)。

任务责任仍属于原任务负责人。当前 Web 统筹负责人负责技术拆分、执行者调度与集成，并按任务独立性、修改冲突和并行收益决定是否委派，不以会话数量衡量进展。收到进展、错误或待办不等于接管相关或无关工作；只有明确分派的范围才进入接收方任务，结果回报给原负责人。当前阶段优先完成 Web 修复；dot 对接和审阅校正服务于该工作，不转移实施责任。

Android 的独立实验进展、错误和待办留在 Android 任务及其 dot 汇报中。跨任务状态只交接 Web 确实需要的共享接口依赖或资源可用性。同步脚本是独立项目工作，不作为 Web 产品需求。临时清理只处理本任务已明确识别的对象。

交接不扩展权限；不得把任务特批、具体额度或自定义确认写入公开仓库。接收方按当前任务授权和项目边界执行。

开发流程规则大修可使用[版本化评估集](evals/development-process/v1/README.md)做同条件对照；普通局部修改仍按影响范围验证。评估文件的静态检查不等于模型行为评估，合成结果不等于真实产品验收。

## 云端审查的使用时机

Codex 仓库设置中的 **Automatic review** 和 **Auto security review** 应保持关闭，保留 GitHub 连接与手动审查能力。所有者于 2026-10-11 确认当时两项均已关闭；此记录不证明此后设置从未变化，发手动请求前若能读取现状应先核对，发现自动审查已开启则避免重复请求并报告。本节是[根目录维护指令](../AGENTS.md#按需触发云端审查)引用的唯一详细流程：仅在本仓库当前开发任务中，具备 GitHub 评论权限的主执行 Agent 可按条件在当前 PR 发请求。所有者已授权这些必要请求，无需逐次确认；不包括其他仓库、历史 PR 补审或云端代改。审阅任务、只读评估、独立审阅者和子 Agent 不再发起。用户明确要求停止、节省本轮额度或暂缓时优先遵守。规则本身不切换云端开关，也不是后台定时器。

**触发评论格式。** 请求评论全文只能是单行 `@codex review` 或 `@codex security review`，不得追加范围说明、其他文字或 HTML 标记。先把范围、风险、完整提交 SHA、审查类型/阶段及去重信息写入 PR 正文或 [PR 审阅跟进](PR_REVIEW_FOLLOWUP.md)，再单独发送标准触发评论；不要将这些上下文拼回触发评论。

**代码审查触发。** 仅涉及重大功能改动的 PR，在基本完成、必要本地检查通过且候选提交已推送后，请求一次 `@codex review`。重大功能包括新增核心能力、跨模块主流程、架构或重要行为变化，以实际影响判断，不以文件数或代码行数判断。日常局部 bugfix、文案、注释、普通说明文档、局部样式和不影响核心行为的小改动跳过代码审查，并记录理由；仅调整审查频率的说明也跳过。数据、配置或规则变化不再单凭文件类型触发代码审查，仍须判断是否构成重大功能改动，并独立检查下述安全风险。用户明确另要代码审查时按其要求执行。

**安全审查独立触发。** 不受上述重大功能门槛限制。改动触及认证/授权、会话/CSRF/Host、凭据/加密、资料外发/网络/SSRF、文件导入或备份恢复的路径与不可信输入、Android 自动备份/迁移、CI 执行不可信代码或敏感权限时，仍请求一次 `@codex security review`，风险范围按上述格式规则提前记录。普通 UI、学习算法或只读文案不自动加安全审查；依赖更新先看依赖审计及实际安全影响。涉及这些边界的规则或配置不能因文字改动、小修复或代码审查已跳过而免除安全风险判断。

**去重与次数。** 发送前读取当前 PR 的请求评论、行内意见及 Code/Security 总结；同类请求已存在或正在运行就等待或读取，不重发。无标记的既有请求也计入。代码审查每个重大功能 PR 一次，不因后续 push、新 SHA、rebase、合并 main、文档变化或问题修复机械重发；修复扩大影响也不自动增加代码审查次数，只有用户明确另要代码审查时才可例外。已授权并发出的请求保留，不因本次频率调整删除或取消。将 `<!-- zhixu-cloud-review kind=code|security phase=initial|followup head=<完整提交SHA> -->` 去重标记写入 PR 正文或审阅跟进记录，替换为实际类型、阶段与 SHA，并注明范围，不放入触发评论；发送后补记对应请求链接；代码审查的 `followup` 仅用于用户明确要求的额外审查。

**安全复审。** 默认零复审：普通问题修复后，定向回归通过且差异核对完成就结束。只有具体残余高风险疑点且现有证据不足以判断修复，或修复实质扩大了跨模块、数据、权限影响时，才可考虑最多一次针对修复的定向安全复审。请求前在 PR 正文或审阅跟进记录写明修复范围、疑点、已有证据、仍缺的判断及预期增益；这是上限，不是必须使用的额度。安全复审的触发评论仍仅为单行 `@codex security review`。超过默认安全审查轮数须所有者明确要求，不能自动扩大为全仓审查。

代码或安全审查次数限制都不降低质量门槛：真实问题继续定向修复或暂停；必要检查、验收或证据缺失时不合并，轮数用尽不等于通过。完成的审查只复用实际已覆盖范围，后续实质改动仍需相应测试与差异核对，不能冒称旧报告已覆盖新改动。回复意见、解决 Review 线程与新发 `@codex` 请求分别计数，不能混作审查次数。

**安全审查的威胁模型入口。** 先复用[架构中的模块边界](ARCHITECTURE.md)与[第一层接口和权限](CHATGPT_MCP.md)，按本机回环服务与会话、Markdown/SQLite 原资料、逐项外发许可与付费预算、加密凭据、网页/导入/模型的不可信输入、备份恢复和 Android 独立存储边界确定本次受影响路径，再写给审查者具体疑点与已做检查；不把未受影响的边界重复当作本轮变更。此处只固定审查入口，不重复维护另一份架构说明；范围提示不保证审查只读这些文件或节省额度。

**失败与记录。** 发送超时或回执不明，先重读 PR 确认评论是否创建；权限、套餐或额度不足则说明阻塞，不换账号或另启审阅者规避。在既有 PR 或审阅跟进记录中留下触发或跳过原因、提交和范围、请求链接、实际请求次数、结果与待处理项。分别记录公开完成状态、可读报告中的具体发现，以及报告不可得时的未知；不能凭完成状态推断安全收益。主执行 Agent 核实意见并按影响范围修复验证；不发送 `@codex fix`、`@codex address that feedback` 等云端代改指令，也不在评论中放真实资料或凭据。手动请求仅控制触发时机，范围提示不保证云端只读指定文件或固定额度；完整安全报告可能有未达 GitHub 显示门槛的发现，不能把“已完成”或“无评论”当完整安全验收。四项 CI、反馈处理和合并前新增意见检查继续执行。

## 发布 0.x 开发预览

1. 用独立 PR 调整 `package.json` 版本并在 CHANGELOG 新增对应版本及日期。修复为 patch，新能力或 0.x 不兼容变化为 minor；不自动升 1.0。
2. PR 合并且 main CI 通过后，在 Actions 手动运行 **Release preview**（main 分支）。此操作由维护 Agent 代办即可。
3. 工作流重新运行完整 CI，检查 main 没有前移、版本和更新说明有效，然后创建不可覆写的 `v0.x.x` tag 与 GitHub 预发布说明。源码下载由 GitHub 自动提供，不打包用户资料。
4. 必须实际查看 Release 页面和工作流成功状态后才声称发布完成。失败时先核对 tag/release 是否已部分创建，不盲目重跑或删除 tag。

若 tag 已创建但 Release 失败：确认 tag 指向该次通过验证的 commit，使用同一 tag 补建 Release（`gh release create --verify-tag`），不移动 tag。已发布的错误通过下一 patch 修正；代码回滚用 revert PR，学习数据另行从备份恢复。

当前发布工作流只支持 0.x.x 且标记为预发布，稳定 1.0 的标准与流程需另行评审。

## 仓库设置与权限

建议 squash 合并、自动删除已合并分支、禁用 force push 与删除 main、要求讨论解决和上述四项检查；单维护者不要求自己无法完成的第二人审批。普通 CI token 只读；仅发布 job 有 contents write。不使用 `pull_request_target` 执行外部 PR 代码。

Actions/Dependabot 可自动检查和提议更新，但许可证选择、公开私有内容、生产 Secret 轮换、不可逆数据操作、套餐付费仍由所有者决定。项目不新增第三方 Agent Skill，现有工具与仓库规则足以覆盖当前流程。
