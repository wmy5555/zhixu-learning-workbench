# ChatGPT 增量保存与结构化导入

用户明确要求保存同一会话时，客户端可在现有 `save_chatgpt_conversation` 工具中提供 `sync`，以后仍更新同一份第一层原始资料。用户消息和助手消息逐字保留；模型摘要和结构化建议单独标注。旧调用不提供 `sync` 时继续沿用第一层快照保存，不自动寻找标题相似的旧资料。

## 保存步骤

1. 用户先授权读取指定历史会话。模型使用已连接的历史读取插件，连续调用 `next_cursor` 到 `has_more:false`。跨页的同一消息须按真实 `message_id`、消息序号及字符位置拼回原文，不能把一个长消息当成几条消息。
2. 将真实会话、分支、快照和消息编号映射到下列字段。没有稳定编号时使用旧快照方式，不能用随机数、消息位置或文本摘要猜测身份。知序工具不会直接调用另一个插件。
3. 首次用 `mode:snapshot`；以后用最后成功回执的 `syncRevision` 填入 `baseRevision`。重试沿用完全相同的 `requestId` 和内容。收到 `saved`、`updated` 或 `already_saved` 才报告成功。
4. 可同时发送结构化整理。知序保存原文后，按顺序导入第二层未核验候选，并返回 `importedNoteIds`。不启动研究、付费模型调用、学习或晋级。

## 接口字段

原有 `requestId/title/summary/messages/coverage/limitations/conversationUrl` 继续使用。增量保存的消息增加 `id`；只接收 `user/assistant` 角色。

| 字段 | 含义 |
| --- | --- |
| `sync.conversationId` | 历史读取器的 `conversation_id`，不是会话标题 |
| `sync.branchId` | 历史读取器的 `branch`；不同分支保存为不同第一层资料 |
| `sync.snapshotId` | 历史读取器的 `snapshot_id`，保留为来源证据 |
| `messages[].id` | 历史读取器的 `message_id`，同一消息再次读取保持一致 |
| `sync.mode` | `snapshot` 或 `delta`；第一次必须是快照 |
| `sync.baseRevision` | 上一次成功回执的 `syncRevision`；更新不可省略 |
| `sync.complete` | 调用方报告本次当前可见分支是否已读到末尾 |
| `sync.readerEvidence.transcriptSha256` | 读取器返回的 `transcript_sha256`；不是简单拼接文本的摘要 |
| `sync.readerEvidence.pages` | 按实际读取顺序记录每页 `range` 和映射后的 `hasMore` |

页范围格式为 `range:{start:{message,offset},end:{message,offset}}`。`message` 为从 0 开始的消息序号，`offset` 为该消息内 JS 字符位置。第一页从 `{message:0,offset:0}` 开始，每页起点必须等于上一页终点。声明 `complete:true` 还要求 `coverage:visible_history`、`mode:snapshot`、末页 `hasMore:false`，最终终点为 `{message:收到的消息总数,offset:0}`，页内位置不越过收到的正文。

服务端只能检查这些字段之间是否一致，无法独立证明模型确实读取了所有网页内容。`complete` 和摘要均是调用方的报告，不是跨插件签名证明；不涵盖隐藏分支、删除记录、附件全文或模型不可见内容。原资料和回执明确保留这一限制。不完整调用保留以前收到但本次没见到的消息，不把缺失消息当成删除，也不沿用上一版完整声明。

## 结构化整理

可选 `structured:{version:1,items:[...]}`。每个条目必须包含：

- `id`：该会话分支中稳定的整理条目编号。
- `title/body`：模型生成的标题和正文。
- `type`：`knowledge`、`conclusion` 或 `unverified_fact`。
- `sourceMessageIds`：非空数组，所有消息必须已收到并保存在同一分支原资料中。
- `uncertainties`：保留具体不确定性或缺失证据的数组；即使空数组，服务端仍添加“未经独立核验”的限制。

三种类型都使用现有第二层 `knowledge/candidate` 容器，分别显示知识建议、模型结论、待验证事实。它们不是已经确认的个人理解，也不直接进入学习。来源记录包含原资料 ID、来源版本、消息编号和类型；原资料更新前的内容仍在历史版本中。条目正文或其所引用的消息改变时创建新的候选版本，保留旧候选及人工编辑。相同条目和相同来源内容不重复新增，也不覆盖已有用户改动。没有重新提供的结构化条目不自动重新解释或加工。

## 冲突与恢复

不同会话或不同分支不会合并。完整快照中的旧消息被删除、旧消息重排、同一消息编号角色改变、片段中新消息插入到无法核对的位置，都返回冲突，要求明确另存分支或重新读取完整范围。完整快照可以补入此前未收到的历史消息，只要已知消息的顺序和身份一致。

不完整快照或增量中的新增消息必须跟在已保存的最后一条消息之后，并在输入中包含这条旧末尾消息作锚点。例如已保存 `A,B,C`，输入 `C,D` 可以追加；输入 `A,D` 或只有 `D` 不能证明位置，必须重新读取足够范围或完整快照。

更新前核对完整文件版本、原文和管理标记。外部或用户编辑过的原资料不自动覆盖。删除、重复 ID、复制的会话标记或原文件身份无法核对时拒绝更新；不会自动重建。已有成功请求的重试仍可返回不含正文的历史回执，不泄露后来的编辑。

多条目导入不是跨 Markdown 文件的原子事务：中断时可能已保存原资料或部分候选，失败不能宣称全部完成。运行记录保留待完成请求；同一请求重试从已保存的内容继续，不重复新增，其他请求须等它完成。原资料已经变化或条目已被删除时停止，不用重试覆盖用户操作。增量运行记录丢失而原文件仍在时，提示人工核对，不猜测旧版本。原文件和全部运行记录同时丢失时无法证明过去的保存状态。

每次提交和累计原文均遵守 200 条消息、50 万字符限制；结构化请求另受 JSON 长度和原有 HTTP 2 MiB 上限约束。继续使用现有 ChatGPT 总开关、专用凭据、独立读取许可、Host/Origin 校验和每分钟最多 30 次新写入限制。所有导入资料保持仅本地，不获取任意修改、删除、权限设置或学习确认能力。
