# ChatGPT 增量保存与结构化导入

## 读回、独立分批与撤销候选

本节描述 2026-10-14 隔离开发候选；不证明正式服务或云端工具已经切换。先检查实际工具和构建摘要，缺少工具时报告版本不配套，不能伪造快照引用。

保存状态与核验结果分别汇报：`verification.status:verified` 证明在该时点实际读回的文件字节、SQLite、消息及候选来源一致；不证明模型摘要或事实正确。`historical_receipt` 只确认过去回执；`preserved_edits` 表示人工内容已保留，不宣称它与模型候选相同。原文和独立结构化候选的每条指纹、数量及三类型计数可核对。

`import_chatgpt_history_batch` 接受已认证且读齐分页的短时引用、独立摘要和可选结构化候选，不接受 `baseRevision`，也不向旧增量会话追加超限消息。每个不可变原文分片保留消息编号、原消息字符偏移、分片及全局指纹；只有全部分片和候选实际读回、全局原文重建一致才返回 `complete:true`。部分成功返回 `partial/pending` 和实际数量；用相同请求、引用与整理内容恢复，不覆盖外部编辑或重建无法确认的已删文件。原始签名快照仍须在 2 MiB 本机传输上限内；超限明确失败，附件字节和隐藏分支不纳入完整声明。

用户指定一次成功回执后，`preview_chatgpt_capture_undo` 仅生成预览。用户在本机「系统 → 写入提案」核对项目并确认才执行；ChatGPT 凭据、`confirm:true` 或外部 MCP 调用均不能代替本机会话及操作凭据。首次保存仅回收该原资料及本次新建候选；增量更新恢复前一逻辑版本，既有复用候选保留。后续编辑、版本或依赖变化会阻止执行，原回执不删除。撤销可再次预览恢复，按相同冲突保护恢复精确原始字节。原文进入可恢复记录，不永久删除；中断会明确报告部分或待继续。整批撤销未实现，分批叶记录不能走普通撤销。

实际回收或替换前，先把当前文件原子移入同目录的隐藏恢复副本，再核对这份实际文件；恢复正文只能独占空位写入，不能替换后来出现的文件。恢复副本与本地操作记录不自动清理，竞争时尽量放回空位，否则保留两份供人工核对。中断后仅在持久操作记录、前后版本清单、目标指纹与删除归属都能核对时承认该步已经完成；不确定的中间状态保留待核对，不猜测后重做。后续人工编辑仍会阻止续跑。

状态中的 `build.sha256` 是进程启动时公开源码输入的摘要，`mcp.build` 属于 MCP 包装进程；两者分别核对。它不是 Git 提交编号，也不证明依赖目录或浏览器账户身份。知序和独立读取器的更新、现有权限、持久凭据及正式服务切换仍分别验收。

用户明确要求保存同一会话时，客户端可在现有 `save_chatgpt_conversation` 工具中提供 `sync`，以后仍更新同一份第一层原始资料。用户消息和助手消息逐字保留；模型摘要和结构化建议单独标注。旧调用不提供 `sync` 时继续沿用第一层快照保存，不自动寻找标题相似的旧资料。

## 从已读取的历史聊天直接导入

用户要求保存指定历史聊天时，历史读取插件先按顺序分页，直到 `has_more:false`。随后调用其 `prepare_zhixu_history_snapshot`，把返回的短时 `historySnapshotRef` 交给知序的 `import_chatgpt_history_snapshot`；模型只填写独立摘要和可选结构化建议，**不重新填写原文**。初次导入不填 `baseRevision`，更新同一会话时填写上次成功回执的 `syncRevision`；重试沿用相同 `requestId`、引用和摘要。

原文在本机两个进程之间通过短时随机命名管道传输，不经模型转写，也不创建公网接口。历史插件只在本次快照的分页连续且确已到末页时提供引用；传输前重新检查读取许可、浏览器账户和当前可见分支正文。发送方使用独立的 32 字节本机密钥对引用和完整快照签名；该密钥以 Windows 当前用户 DPAPI 加密保存在历史读取器的本机配置目录，知序在同一 Windows 用户下解密并验签。它不出现在管道名、模型结果或仓库中；首次创建持久密钥需用户另行批准，未配置或验签失败时不会保存。知序再核对消息编号、顺序、分页、正文摘要和签发/到期时间，走下文相同的版本冲突与防覆盖规则。这证明同用户密钥持有者发送了数据，不能区分同一用户下所有可访问密钥的程序。引用最多五分钟有效，过期或聊天变化需从第一页重新读取。单条导入仍受 200 条消息、50 万字符和本机 2 MiB 传输上限限制；超限会明确失败，不截断成“完整”。隐藏分支、隐藏推理、图片及附件字节仍不在导入范围内。历史插件的“允许读取”和知序的 ChatGPT 接入开关都必须保持开启；知序的知识库读取开关不是保存的前提。

## 手动传入消息的兼容方式

1. 用户先授权读取指定历史会话。模型使用已连接的历史读取插件，连续调用 `next_cursor` 到 `has_more:false`。跨页的同一消息须按真实 `message_id`、消息序号及字符位置拼回原文，不能把一个长消息当成几条消息。
2. 将真实会话、分支、快照和消息编号映射到下列字段。没有稳定编号时使用旧快照方式，不能用随机数、消息位置或文本摘要猜测身份。知序工具不会直接调用另一个插件。
3. 首次用 `mode:snapshot`；以后用最后成功回执的 `syncRevision` 填入 `baseRevision`。重试沿用完全相同的 `requestId` 和内容。收到 `saved`、`updated` 或 `already_saved` 才报告成功。
4. 可同时发送结构化整理。知序保存原文后，按顺序导入第二层未核验候选，并返回 `importedNoteIds`。不启动研究、付费模型调用、学习或晋级。

## 原始资料来源信息

新保存的原文定位使用读取时的真实会话标题，而不是摘要标题、消息数量或版本号。独立分片的资料标题仍有分片编号，但来源定位保留不带分片后缀的原会话标题。普通保存必须提供已知完整 `conversationUrl`；历史交接使用经认证的 `conversation_id` 对应 `https://chatgpt.com/c/<id>`，不创建分享链接。

可选 `conversationDate` 为可核对的原资料日历日期（`YYYY-MM-DD`），`conversationDateBasis` 说明日期来源和语义；未知则省略或留空。当前历史交接没有平台会话创建日期，因此只取 `units[0].created_at` 的日历日期，保留原有时区中的日期、不转换为服务器日期，并记录原时间及消息编号。它表示“当前可见分支首条消息日期”，不保证是会话最初创建日。首条日期缺失或格式异常时留空，不选择后续消息、不用 `updated_at`、`issued_at` 或导入时间代替。

界面在资料日期旁显示“导入时日期依据”，原始出处保留同一依据，收集时间仍独立保存为 `acquiredAt`。手动传入的信息不增加独立核验承诺。此变更只用于新保存/明确更新，不扫描修补已有历史资料；旧回执与中断重试使用原元信息版本，人工改动仍受哈希保护。

## 接口字段

原有 `requestId/title/summary/messages/coverage/limitations/conversationUrl` 继续使用。增量保存的消息增加 `id`；只接收 `user/assistant` 角色。

| 字段 | 含义 |
| --- | --- |
| `sync.conversationId` | 历史读取器的 `conversation_id`，不是会话标题 |
| `sync.branchId` | 历史读取器的 `branch`；不同分支保存为不同第一层资料 |
| `sync.snapshotId` | 历史读取器的 `snapshot_id`，保留为来源证据 |
| `messages[].id` | 历史读取器的 `message_id`，同一消息再次读取保持一致 |
| `sync.mode` | `snapshot` 或 `delta`；第一次必须是快照 |
| `sync.baseRevision` | 上一次成功回执的 `syncRevision`；更新不可省略 |
| `sync.complete` | 调用方报告本次当前可见分支是否已读到末尾 |
| `sync.readerEvidence.transcriptSha256` | 读取器返回的 `transcript_sha256`；不是简单拼接文本的摘要 |
| `sync.readerEvidence.pages` | 按实际读取顺序记录每页 `range` 和映射后的 `hasMore` |

页范围格式为 `range:{start:{message,offset},end:{message,offset}}`。`message` 为从 0 开始的消息序号，`offset` 为该消息内 JS 字符位置。第一页从 `{message:0,offset:0}` 开始，每页起点必须等于上一页终点。声明 `complete:true` 还要求 `coverage:visible_history`、`mode:snapshot`、末页 `hasMore:false`，最终终点为 `{message:收到的消息总数,offset:0}`，页内位置不越过收到的正文。

对手动传入消息的兼容方式，服务端只能检查这些字段之间是否一致，无法独立证明模型确实读取了所有网页内容。`complete` 和摘要均是调用方的报告，不是跨插件签名证明；不涵盖隐藏分支、删除记录、附件全文或模型不可见内容。原资料和回执明确保留这一限制。不完整调用保留以前收到但本次没见到的消息，不把缺失消息当成删除，也不沿用上一版完整声明。本机快照直接导入另外核对了历史插件的实际快照，但也不代表读取了附件字节或其他分支。

## 结构化整理

可选 `structured:{version:1,items:[...]}`。每个条目必须包含：

- `id`：该会话分支中稳定的整理条目编号。
- `title/body`：模型生成的标题和正文。
- `type`：`knowledge`、`conclusion` 或 `unverified_fact`。
- `sourceMessageIds`：非空数组，所有消息必须已收到并保存在同一分支原资料中。
- `uncertainties`：保留具体不确定性或缺失证据的数组；即使空数组，服务端仍添加“未经独立核验”的限制。

三种类型都使用现有第二层 `knowledge/candidate` 容器，分别显示知识建议、模型结论、待验证事实。它们不是已经确认的个人理解，也不直接进入学习。来源记录包含原资料 ID、来源版本、消息编号和类型；原资料更新前的内容仍在历史版本中。条目正文或其所引用的消息改变时创建新的候选版本，保留旧候选及人工编辑。相同条目和相同来源内容不重复新增，也不覆盖已有用户改动。没有重新提供的结构化条目不自动重新解释或加工。

## 冲突与恢复

不同会话或不同分支不会合并。完整快照中的旧消息被删除、旧消息重排、同一消息编号角色改变、片段中新消息插入到无法核对的位置，都返回冲突，要求明确另存分支或重新读取完整范围。完整快照可以补入此前未收到的历史消息，只要已知消息的顺序和身份一致。

不完整快照或增量中的新增消息必须跟在已保存的最后一条消息之后，并在输入中包含这条旧末尾消息作锚点。例如已保存 `A,B,C`，输入 `C,D` 可以追加；输入 `A,D` 或只有 `D` 不能证明位置，必须重新读取足够范围或完整快照。

更新前核对完整文件版本、原文和管理标记。外部或用户编辑过的原资料不自动覆盖。删除、重复 ID、复制的会话标记或原文件身份无法核对时拒绝更新；不会自动重建。已有成功请求的重试仍可返回不含正文的历史回执，不泄露后来的编辑。

多条目导入不是跨 Markdown 文件的原子事务：中断时可能已保存原资料或部分候选，失败不能宣称全部完成。运行记录保留待完成请求；同一请求重试从已保存的内容继续，不重复新增，其他请求须等它完成。原资料已经变化或条目已被删除时停止，不用重试覆盖用户操作。增量运行记录丢失而原文件仍在时，提示人工核对，不猜测旧版本。原文件和全部运行记录同时丢失时无法证明过去的保存状态。

写原资料前先持久保存写入阶段。如果在记录“开始写入”之前中断，尚未写文件，原请求可恢复；一旦记录开始写入，缺失文件就不能证明它从未创建，重试会停止并要求在知序核对，避免复活外部删除。记录开始写入后、实际创建之前中断也属于无法确定的范围。已经存在且身份、内容和版本一致的文件可继续导入；旧待完成记录没有写入阶段、原文件也不在时，保守拒绝自动重建，不做自动迁移。

每次提交和累计原文均遵守 200 条消息、50 万字符限制；结构化请求另受 JSON 长度和原有 HTTP 2 MiB 上限约束。继续使用现有 ChatGPT 总开关、专用凭据、独立读取许可、Host/Origin 校验和每分钟最多 30 次新写入限制。所有导入资料保持仅本地，不获取任意修改、删除、权限设置或学习确认能力。
