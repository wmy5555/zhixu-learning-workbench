# 子智能体委派

将边界清楚的工作交给子智能体，同时让主智能体掌握全局判断和最终结果。遵守仓库根目录及目标目录的 AGENTS.md、用户当前指令和运行环境规则；本技能不改变其优先级。

## 先决定是否委派

确认当前规则允许委派，且任务具备独立产物、明确完成条件与可控写入范围。只有能缩短关键路径、隔离大量无关上下文或提供已要求的独立核对，且收益超过交接成本时才委派。微小修改、强耦合决策和无法划清边界的任务由主智能体处理。

工具不可用或规则禁止委派时，直接完成能完成的工作；确实缺少必要能力时报告限制。不要通过另建用户聊天、切换工具或继续下级委派绕过限制。

## 派发任务

1. 按 [任务契约](references/contracts.md) 选 Light、Standard 或 Strict，填写任务目标、路径与写入范围、验收、验证和固定返回结构。契约可直接放在派发消息中，不为普通任务另建文档。
2. 按 [模型与上下文](references/model-routing.md) 重新判断任务配置，记录一句选择理由；传递必要文件、已确认事实与未解决问题，不复制秘密或无关历史。使用当前工具支持的参数。
3. 明确文件及共享资源负责人。有重叠就拆分职责或串行；独立工作区仍需协调公共接口、锁文件、数据库、服务和测试端口。检查已有改动，不能覆盖他人未提交内容。
4. 编码任务或需要复用检查时，按 [验证与接收](references/verification.md) 指定执行负责人和证据要求。只读审阅只读差异及证据，不安排重复测试。
5. 派发后主智能体继续独立工作，按工具支持的等待机制接收结果，避免高频轮询。子智能体发现范围外问题时先回报，不自行扩大范围、合并或改动共享服务。

## 异常与接收

- `NEEDS_CONTEXT`：补充具体缺失信息；未确定的架构或接口由主智能体决定。
- `BLOCKED`：核对权限、依赖或环境障碍；保留已完成产物，只推进不受阻工作，不盲目重试。
- `DONE_WITH_CONCERNS`：逐项处理疑点，必要条件缺失时不验收为完成。
- `DONE`：按契约核对实际差异、可定位证据和未验证边界，再集成。不要仅凭状态文字判定通过。

同一失败没有新线索时停止相同重试，重新判断范围、上下文或配置。只有具体缺陷或新增改动才做定向修复和补验；达到项目完成条件即结束。

沿用已有任务的配置仍需适合新工作；只是同一任务的补充和修复时保留原契约，并明确变化。经验仅使用可核对的结果，不估算节省比例；持久记忆只在用户明确要求时更新。
